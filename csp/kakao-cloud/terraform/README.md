# Narwhal IDP on Kakao Cloud - Terraform Infrastructure

English | [Korean](README.ko.md)

OpenTofu project that provisions VM infrastructure on Kakao Cloud for the Narwhal IDP cluster.
Kubernetes and the platform apps are installed afterwards by
[`scripts/cloud/provision-kakao.sh`](../../../scripts/cloud/provision-kakao.sh).

Verified end to end on 2026-07-27: 6/6 nodes Ready, 33 ArgoCD applications Synced/Healthy,
services reachable through the worker LB.

## What Gets Created

| Resource | Count | Description |
|----------|-------|-------------|
| VPC | 1 | 172.16.0.0/16 |
| Subnet | 1 | 172.16.0.0/24 |
| Security Group | 1 | K8s + Cilium + NFS + proxy/registry ports |
| Master VMs | 3 | Control-plane (t1i.large, 2 vCPU / 4GB), fixed **private** IPs .10 .11 .12 |
| Worker VMs | 3 | Data-plane (t1i.xlarge, 4 vCPU / 8GB), fixed **private** IPs .21 .22 .23 |
| Bastion VM | 1 | SSH jump host, forward proxy, airgap registry (public + private .207) |
| Master LB | 1 | K8s API (6443) + etcd (2379) |
| Worker LB | 1 | Ingress HTTP (80) + HTTPS (443) -> NodePort 31080/31443 |
| Public IPs | 3 | Bastion + 2 LBs. **Cluster nodes have none** |

Nodes are private by design. Everything reaches them through the bastion, and their
outbound traffic goes through a squid proxy running there — Kakao Cloud provider 0.5.1 (and 0.4.4 before it)
exposes no NAT gateway resource, and giving each node a public IP would expose the SSH
and 6443 rules this security group opens to 0.0.0.0/0. `assign_node_public_ips = true`
is the escape hatch if you need direct egress instead.

## Architecture

```
                            Internet
                                |
        +-----------------------+-----------------------+
        |                       |                       |
    Bastion                 Master LB               Worker LB
  public IP (+priv .207)   public IP :6443       public IP :80/443
  ssh · squid:3128            |                       |
  registry:5000               |                       |
        |                     |                       |
        |  ProxyJump          | private VIP .236      | private VIP .110
        |  (admin access)     |                       | -> NodePort 31080/31443
        v                     v                       v
   +---------------------------------------------------------+
   |  > Nodes hold private addresses only - no public IP      |
   |                                                          |
   |  master-1 .10   master-2 .11   master-3 .12              |
   |  worker-1 .21   worker-2 .22   worker-3 .23              |
   |                                                          |
   |  egress -> bastion squid:3128                            |
   +---------------------------------------------------------+
                    VPC 172.16.0.0/16 · Subnet 172.16.0.0/24
        (every .xx above is a 172.16.0.xx private address)
```

## Prerequisites

- **OpenTofu** >= 1.13.0 (`tofu`; Terraform CLI also works)
- **Kakao Cloud Account** with Application Credential (ID + Secret)
- **Quotas**: 7 instances, 26 vCPU, 52GB+ RAM, 1.2TB volume, 3 public IPs, 2 LBs

The SSH keypair is generated by this project (`tls_private_key` + `kakaocloud_keypair`)
and written to `var.ssh_key_path`; you do not pre-register one.

## Quick Start

```bash
cd csp/kakao-cloud/terraform

cp terraform.tfvars.example terraform.tfvars
# Fill in application_credential_id / application_credential_secret

tofu init
tofu plan
tofu apply
```

Then, from the repo root, bring up the cluster:

```bash
./scripts/cloud/stage-kakao-nodes.sh     # repo -> nodes, in the layout the scripts expect
./scripts/cloud/provision-kakao.sh all   # proxy -> base -> mirror -> init -> join -> nfs -> phase1 -> phase2
```

`provision-kakao.sh` reads every address from OpenTofu state, so nothing is typed twice.
Stages are idempotent (sentinels under `/home/vagrant/.narwhal-stage/`); `FORCE=1` re-runs one.

## After Deployment

Nodes have no public IP, so every hop goes through the bastion. Register both in
`~/.ssh/config` once:

```bash
tofu output -raw ssh_config >> ~/.ssh/config
ssh narwhal-master-1
```

That writes `narwhal-bastion` plus `narwhal-master-1..3` / `narwhal-worker-1..3`, each
carrying the key and `ProxyJump narwhal-bastion`.

Command-line `-J` does **not** work here: it starts a separate ssh process for the jump
host and does not pass the command line's `-i`, so the bastion hop fails with
`Permission denied (publickey)`. `-o IdentityFile` does not reach it either. Use the
config above, or name the key for both hops with `ProxyCommand` —
`tofu output -json bastion_ssh` prints ready-to-run commands in that form.

`master_public_ips` and `worker_public_ips` are empty arrays unless
`assign_node_public_ips` is on — that is expected, not a failure.

## Cluster Access

### kubectl from your machine

`scripts/cloud/set-config-kakao.sh` does all of the below in one step — opens the
tunnel, pulls the CA and client certs, and registers a `narwhal-kakao` context:

```bash
scripts/cloud/set-config-kakao.sh          # cert, the default
scripts/cloud/set-config-kakao.sh token    # service account token, 1 year
scripts/cloud/set-config-kakao.sh oidc     # Keycloak, needs kubelogin + /etc/hosts
```

It reuses an existing tunnel, and `PORT=7443 ...` moves it if 6443 is taken. The
contexts are `narwhal-kakao`, `narwhal-kakao-token`, `narwhal-kakao-oidc` — named so
they never collide with a local Vagrant one. This is the cloud counterpart of
`scripts/common/set-config.sh`.

The manual equivalent, and why a tunnel is needed at all:

The apiserver certificate carries `localhost`, `127.0.0.1`, the master private IPs and the
private VIP — **not the LB's public IP**. Connecting straight to the public endpoint fails
TLS verification, so tunnel to a name the certificate already covers.

Assumes the `~/.ssh/config` entries above. Paste-safe: no inline comments, because an
interactive zsh with `interactive_comments` off treats `#` as a normal word.

```bash
mkdir -p ~/.kube
ssh narwhal-master-1 'sudo cat /etc/kubernetes/admin.conf' > ~/.kube/kakao.conf
sed -i '' 's#server: https://.*#server: https://127.0.0.1:6443#' ~/.kube/kakao.conf

ssh -f -N -L 6443:127.0.0.1:6443 narwhal-master-1
KUBECONFIG=~/.kube/kakao.conf kubectl get nodes
```

`admin.conf` is root-owned on master-1, hence `sudo cat` rather than scp. `sed -i ''` is
macOS — GNU sed wants plain `-i`. The third command opens the forward in the background.

Verified 2026-07-29: six nodes and 33 ArgoCD applications listed from the operator host.
Close the tunnel with `pkill -f '6443:127.0.0.1:6443'`.

To reach the API by its public address instead, add the LB's public IP to `certSANs` in
`02-init-cluster.sh` and regenerate the apiserver certificate — do not disable TLS
verification.

### kubectl on a node

```bash
ssh narwhal-master-1
sudo -E env KUBECONFIG=/home/vagrant/.kube/config-local kubectl get nodes
```

`sudo -E` alone does not carry your environment on these images (§ Known Issues in
`docs/kakao/cloud-deployment.md`), so pass `KUBECONFIG` explicitly as shown.

### Web UIs

`*.kakao.narwhal.internal` has no public DNS; the names are served by the worker LB.
The domain differs from Vagrant's `local.narwhal.internal` on purpose — both clusters
serve the same service names and both resolve only through `/etc/hosts` on your machine,
so a shared domain would have them overwrite each other's entries.

Map them once:

```bash
scripts/cloud/setup-hosts-kakao.sh --apply
```

Hostnames are read from the cluster's ApisixRoutes, written between
`# BEGIN narwhal-kakao` markers, and removable with `--remove`. The command also exports
the platform CA and prints how to trust it — certificates are issued by
`CN=Narwhal IDP Root CA`, so browsers warn until you do.

### Service accounts and passwords

Every credential the platform generates is printed by one script:

```bash
ssh narwhal-master-1 'sudo env KUBECONFIG=/home/vagrant/.kube/config-local DOMAIN=kakao.narwhal.internal bash /home/vagrant/scripts/test/show-credentials.sh'
```

It covers Keycloak (admin plus the pre-seeded `admin`/`dev`/`view`/`guest` realm users),
ArgoCD, Gitea, Harbor, Grafana, OpenBao root and unseal keys, the APISIX admin API key,
PostgreSQL service credentials and the OIDC client secrets. Its closing "SSH / Node access"
block still prints Vagrant addresses — use `tofu output` for this deployment's.

For a single value:

```bash
kubectl get secret <name> -n <ns> -o jsonpath='{.data.<key>}' | base64 -d
```

Web UIs are behind Keycloak SSO at `https://<service>.kakao.narwhal.internal`, reached
through the worker LB. Point the hostname at it with `--resolve` or an `/etc/hosts` entry:

```bash
LB=$(tofu output -raw worker_lb_public_ip)
curl -sk --resolve "argocd.kakao.narwhal.internal:443:$LB" https://argocd.kakao.narwhal.internal/
```

## Directory Structure

```

  bastion.tf           # Jump host + its public IP
  variables.tf         # Variable definitions
  outputs.tf           # Node IPs, LB endpoints, bastion, ssh_key_path, subnet_cidr, vpc_cidr
  provider.tf          # kakaocloud provider v0.5.1
  cloud-init.yaml      # Basic VM init (SSH pubkey only)
  terraform.tfvars.example
  modules/
    network/           # VPC + Subnet
    security/          # Security Group
    compute/           # Master/Worker VMs (fixed private IPs) + optional public IPs
    loadbalancer/      # Master LB (6443/2379) + Worker LB (80/443)
```

## Configuration

Key settings in `terraform.tfvars`:

| Variable | Default | Description |
|----------|---------|-------------|
| `master_count` | 3 | Master nodes (3 for HA) |
| `worker_count` | 3 | Worker nodes |
| `master_flavor` | t1i.large | 2 vCPU, 4GB RAM |
| `worker_flavor` | t1i.xlarge | 4 vCPU, 8GB RAM |
| `volume_size` | 200 | Disk size in GB |
| `availability_zone` | kr-central-2-a | Kakao Cloud AZ |
| `assign_node_public_ips` | false | Direct egress per node instead of the bastion proxy |

Node IPs are pinned contiguously (`cidrhost` on `subnet_cidr`) so the install scripts'
`${MASTER_IP_BASE}${idx}` arithmetic resolves the same way it does under Vagrant.

| 111, 2049 | VPC | NFS (rpcbind, nfsd) |

## Upgrading an existing deployment to provider 0.5.1

Provider 0.5.0 removed `kakaocloud_vpc.subnet`, and the bastion's `initial_security_groups`
cannot be changed in place (`Changing the initial security group is not allowed`, even with
`-replace`; pending #202). A fresh install needs none of this. A live deployment needs the
steps below, in order, run from this directory with the operator's `terraform.tfvars`.

```bash
# 1. Back up state, and note the default subnet CIDR while the 0.4.x schema still shows it
tofu state pull > ~/narwhal-kakao-state-pre-0.5.1.json   # keep outside git
tofu state show module.network.kakaocloud_vpc.vpc        # the `subnet` block has only cidr_block/az, NO id:
# look up the subnet ID with that CIDR (named "main") in the Kakao Cloud console (VPC > Subnet),
# or with a throwaway config using `data "kakaocloud_subnets"` (read-only)

# 2. Pull the new provider (the lock file is already pinned to 0.5.1)
tofu init   # the committed lock already pins 0.5.1; -upgrade would re-resolve it

# 3. Import the VPC default subnet (the former inline `subnet` block)
tofu import module.network.kakaocloud_subnet.vpc_default_subnet <default-subnet-id>

# 4. Pin the bastion's current private IP: nodes use it as DNS, squid proxy and registry mirror
tofu output -raw bastion_private_ip   # set this value as bastion_private_ip in terraform.tfvars

# 5. Replace the bastion alone. -replace is refused for the old bastion (see above), and a
#    targeted destroy would also destroy its public IP (prevent_destroy then errors).
#    Take the address out of state first, destroy the instance, recreate, re-import:
tofu show -json | jq -r '.values.root_module.resources[] | select(.address=="kakaocloud_public_ip.bastion_public") | .values.id'   # record <public_ip_id> BEFORE state rm
tofu state rm kakaocloud_public_ip.bastion_public
tofu destroy -target=kakaocloud_instance.bastion -refresh=false
tofu apply -target=kakaocloud_instance.bastion      # new bastion; its address is not attached yet
tofu import kakaocloud_public_ip.bastion_public <public_ip_id>
tofu apply                                          # re-associates the kept address (in-place update)

# 6. Rebuild what lived on the bastion (squid, registry) from the repo root
cd ../../..
./scripts/cloud/provision-kakao.sh proxy registry
```

Notes:

- Read `tofu plan` after steps 3 and 4. The only expected change is the bastion replacement;
  the imported subnet should plan no change (the `vpc_default_subnet_name` default is `main`).
- The `proxy` stage has no sentinel and always re-runs. The `registry` stage skips when the
  bastion already serves `:5000`; a new bastion does not, so `FORCE=1` is only needed to
  re-push into a bastion registry that is still alive. Sentinel-guarded node stages
  (`base`, `mirror`, ...) are not redone.
- The new bastion has a new SSH host key; clear the old entry from `known_hosts`.
- Every `kakaocloud_public_ip` carries `prevent_destroy` (D-PUBIP), so the address survives
  VM and LB recreation. Once the bastion is on 0.5.1, future replacements use `-replace`
  (next section) and need none of the state surgery in step 5.

## NFS data volume (Kakao)

`nfs_data_volume_size` (GB, default `0` = disabled, otherwise 50..16384) creates a dedicated
block volume `<master_name>-1-nfs-data` and attaches it to master-1. `scripts/cluster/01-nfs-server.sh`
formats it XFS (label `narwhal-nfs`) and mounts it on `/srv/nfs/k8s` with `prjquota`, which
`nfs-quota-agent` needs (XFS project quota can only be enabled at the initial mount, never by remount).
The volume has `prevent_destroy` (D-NFS-VOL) and is attached with `is_delete_on_termination = false`.

Apply in four gated steps. `-target` is the deliberate exception to the usual "never target"
rule here, and it is required: a full plan after the attach is not clean. Updating master-1
in place makes its computed `addresses` unknown during apply, which forces replacement of
the four load balancer target-group members (etcd, master, master_http, master_https `["0"]`)
that read `address` from it. Create the volume, attach it alone, then confirm the plan converges.

```bash
# a) create the volume only
tofu plan -target=module.compute.kakaocloud_volume.nfs_data -out=s1.tfplan
#    STOP unless exactly 1 to add, 0 to change, 0 to destroy
tofu apply s1.tfplan

# b) attach it to master-1 only
tofu plan -target='module.compute.kakaocloud_instance.master[0]' -out=s2.tfplan
#    STOP unless 0 to add, 1 to change, 0 to destroy, and the volumes diff is +1 element
#    (id = the new volume, is_delete_on_termination = false) with the root element unchanged
tofu apply s2.tfplan

# c) confirm convergence
tofu plan
#    STOP unless "No changes". Any LB member "must be replaced": stop, refresh, re-plan
```

d) On master-1, before running `01-nfs-server.sh`:

```bash
ls -l /dev/disk/by-id/virtio-<first 20 chars of the volume id>
sudo blkid -p /dev/disk/by-id/virtio-<first 20 chars of the volume id>   # must print nothing
```

STOP unless the link exists and `blkid` prints nothing (a blank volume).

The device appears in the VM as `/dev/disk/by-id/virtio-<first 20 chars of the volume id>`
(virtio-blk serial). `scripts/cloud/provision-kakao.sh` derives it from the `nfs_data_volume_id`
output and passes it as `NFS_DATA_DEVICE`; override it by exporting `NFS_DATA_DEVICE` yourself.

Migrating the data already on the ext4 root disk is a separate, approval-gated runbook:
`docs/runbooks/nfs-xfs-migration.md`. `01-nfs-server.sh` refuses to mount over a non-empty `/srv/nfs/k8s`.

## Replacing a VM

Public IPs (bastion, node egress, both LBs) are external endpoints: DNS, kubeconfig, operator
SSH and allowlists point at them. Keep the address by replacing the VM, not destroying it:

```bash
tofu apply -replace=kakaocloud_instance.bastion   # plan shows the public IP "updated in-place"
```

- Never `tofu destroy -target=<instance>`: it also destroys the dependent public IP, and
  with the guard it now errors instead.
- `initial_security_groups` cannot change in place. Swapping a security group therefore still
  means recreating the instance: do it with `-replace` above, not with a targeted destroy.
- If `-replace` itself is blocked by the provider, use the step 5 sequence above
  (`tofu state rm` the public IP, destroy the instance, recreate, `tofu import`, apply).
  After the import, read `tofu plan`: the public IP must show `update in-place`. If it shows
  replace, `prevent_destroy` blocks it by design; stop and investigate, do not remove the guard.
  This state rm / import sequence has not yet been verified against a live deployment.
- Root-level resources sit under `.values.root_module.resources[]` in the `tofu show -json`
  query; a resource inside a module is under `.values.root_module.child_modules[]`.

## Cleanup

`kakaocloud_public_ip` resources are guarded by `prevent_destroy` (D-PUBIP), so a plain
`tofu destroy` fails with `Instance cannot be destroyed`. To tear everything down, drop the
guard first, either by removing the lifecycle blocks or by releasing the addresses from state:

```bash
# Option A: remove the guards (all five resources), then destroy; the addresses are released
sed -i.bak '/prevent_destroy = true/s/true/false/' bastion.tf modules/compute/main.tf modules/loadbalancer/main.tf
tofu destroy
# restore the guards afterwards: mv bastion.tf.bak bastion.tf (and the two module files)

# Option B: keep the addresses outside OpenTofu (they stay allocated and billed until you
# release them in the Kakao Cloud console: VPC > Public IP)
tofu state list | grep kakaocloud_public_ip | xargs -n1 tofu state rm
tofu destroy
```

`assign_node_public_ips = false` on a live cluster is blocked by the same guard, and so is
scaling `master_count` / `worker_count` down while `assign_node_public_ips = true` (the removed
index's address would be destroyed); use option B for those addresses first.

52 of the 53 resources go in ~15 minutes. **VPC deletion alone can stretch into hours.**

Measured 2026-07-29: with everything else already gone, the VPC delete printed
`Still destroying...` for **1h54m** before being interrupted. A later `tofu refresh` still
keeps the VPC in state, but its real condition is this:

```bash
tofu state show module.network.kakaocloud_vpc.vpc | grep provisioning_status
#   provisioning_status = "PENDING_DELETE"
```

`PENDING_DELETE` means neither alive nor gone, and the distinction matters because a VPC
in that state cannot be reused. Leaving it in place and running `tofu apply` dies here:

```
Error: create resource: kakaocloud_subnet
VPC status is 'PENDING_DELETE'.
```

`tofu plan` looks perfectly healthy first — `47 to add, 0 to destroy` — so do not judge
from the plan. **Always check `provisioning_status`.**

Waiting is the only move. Once the delete lands and the VPC drops out of state, `tofu
apply` recreates all 48 resources including the VPC. Poll for it:

```bash
until ! tofu state list | grep -q kakaocloud_vpc.vpc; do
  tofu refresh -input=false >/dev/null 2>&1
  sleep 300
done
tofu apply
```

Interrupting costs no data — the delete keeps running server-side, and re-running
`tofu destroy` gets you nothing that waiting does not.

## Known Issues

None open in this project. Two behaviours worth knowing before you debug something else:

- **Load balancers must not be created before the instances.** A `kakaocloud_load_balancer`
  takes its private VIP from the same subnet by automatic allocation, `private_vip` is
  computed and cannot be pinned, and `kakaocloud_subnet` exposes no allocation pool. An LB
  created first will take an address the compute module pinned — that is why
  `module.loadbalancer` carries `depends_on = [module.compute]`.
- **A module-level `depends_on` also defers that module's data sources to apply time.**
  Adding one security group rule once planned as a full rebuild of every running instance,
  because `data.kakaocloud_images` became unknown and `image_id` forced replacement. Keep
  those lists as narrow as the real dependency.

Provisioning-side issues (the container runtime, unattended-upgrades, NFS) are documented
in [`docs/common/lessons-log.md`](../../../docs/common/lessons-log.md).
