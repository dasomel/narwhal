## 배경

플랫폼 인프라에서 작동하는 자율 AI 에이전트는 강력한 거버넌스와 부인 방지(non-repudiation)를 필요로 한다.
Narwhal 이슈 #73 및 OpenForge ADR-0013은 다음과 같은 4가지 독립된 책임을 분리하는 거버넌스 아키텍처를 규정한다:

- **정책 결정 지점 (Policy Decision Point, PDP):** 요청을 인가하고 암호학적으로 제한된 1회성(spend-once) 인가 토큰(grant)을 발급한다.
- **서명기 (Signer):** 에이전트 런타임과 격리된 경계에서 비공개 서명 키를 안전하게 관리한다.
- **정책 집행 지점 (Policy Enforcement Point, PEP):** 에이전트의 도구 호출을 가로채고, PDP와 상호작용하여 인가를 소비하며, 증적을 기록하고 실행기를 호출한다.
- **실행기 (Executor):** 인가된 도구 호출, 워크로드 또는 인프라 변경 작업을 실제로 수행한다.

혼동 대리인(confused deputy) 공격, 권한 상승, 부인 방지를 방지하기 위해 인가 토큰은 반드시 1회만 소비되어야 한다.
그러나 1회성 토큰만으로는 완전한 책무성을 보장할 수 없다. 에이전트 런타임이나 호스트가 침해당하면 정책 외부의 행동을
수행하거나, 감사 로그를 누락하거나, 과거 기록을 조작할 수 있기 때문이다.

따라서 런타임이 침해당한 후에도 무결성을 검증할 수 있는 불변 실행 증적 체인(tamper-evident evidence chain)이 필요하다.

### 위협 모델 (Threat Model)

에이전트 런타임 내부에서 임의 코드가 실행되거나 PEP가 동작하는 호스트 환경이 침해되었다고 가정한 공격자 모델이다.
공격자는 로컬 파일 및 프로세스 메모리에 접근할 수 있으며 다음과 같은 공격을 시도할 수 있다:

1. **쓰기 중단 (Stop writing / 은폐):** 비인가 도구를 탐지 없이 실행하기 위해 디스크 로그 추가를 중단한다.
2. **재작성 및 위조 (Rewrite / forge / 변조):** 과거 기록의 타임스탬프, 인자, 실행 결과를 변조하거나 위조된 서명으로 가짜 기록을 삽입한다.
3. **꼬리 자르기 (Truncate tail):** 최근 악의적인 실행 기록을 은폐하기 위해 로그 파일의 끝부분을 잘라낸다.
4. **롤백 및 포크 (Roll back / fork):** 과거 정상 상태로 체인을 되돌리고 유효한 서명을 가진 다른 분기 기록으로 대체한다.
5. **재시작 후 인가 재사용 (Replay a grant after restart):** 프로세스나 호스트를 강제 재부팅한 뒤 이미 소비된 1회성 인가 토큰을 재제출하여 중복 실행을 시도한다.
6. **소비 후 결과 누락 (Drop the result after consuming):** intent 기록 후 도구를 실행하고 인가를 소비했으나, 결과(result) 기록을 의도적으로 삭제/누락하여 실행되지 않았다고 주장하거나 혼란을 유도한다.

### 벤더 중립성 및 기존 프로토타입 평가

본 아키텍처는 벤더 중립적이고 전송 계층에 독립적이며, 특정 LLM 제공자나 에이전트 프레임워크에 종속되지 않는다.

Narwhal #73 검토 과정에서 외부 프로토타입(`shagunlabs/mcp-guard`)을 평가했다. 그러나 검토 당시 해당 저장소의
README는 핵심 감사 기능에 대해 "Not yet built"로 명시하고 있었으며, 암호학적 체크포인트, 2단계 intent-result 순서 보장,
오프라인 엄격 검증 기능이 부재했다. 이에 따라 해당 프로젝트를 채택하거나 의존하지 않고 독립적인 표준 규격을 수립했다.

## 결정

증적 체인 아키텍처는 구속력을 갖는 결정(D-EV-1 ~ D-EV-42)으로 정의된다.

### D-EV-1: 역할 및 키 분리

체인은 다음과 같이 아키텍처 역할을 엄격히 분리한다:

- **작성기 (Writer, PEP 측):** 로컬 체인에 항목을 추가한다. 작성기는 비공개 서명 키를 **절대로 보유하지 않는다.**
- **서명기 (Signer):** 비공개 키를 보유한 별도 프로세스다. 참조 구현 `OpensslSigner(key_path)`는 D-EV-10에 따라 메시지 바이트를
  격리된 0600 임시 파일로 작성한 뒤 `openssl pkeyutl -sign -rawin -inkey KEY -in MSG_FILE` 서브프로세스를 실행하여
  원시 서명 바이트를 반환한다.
- **검증기 (Verifier):** 공개 검증 키만을 사용하여 `openssl pkeyutl -verify -pubin -inkey PUB -rawin -sigfile SIG`로 증적 무결성을 평가한다.
- **키 분리:** 서로 다른 두 개의 Ed25519 키쌍이 필수적이다:
  1. `entry_pub` (인스턴스 키): 개별 실행 항목에 서명한다.
  2. `cp_pub` (체크포인트 카운터서명 키): 체크포인트 요약에 서명한다.
  두 공개 키가 동일할 경우 검증은 **반드시 실패**해야 한다.

- **근거:** 침해 영향 범위를 최소화한다. PEP 호스트가 장악되더라도 서명 프로세스가 격리되어 있으면 공격자가 임의 서명을 위조할 수 없다. 또한 분리된 체크포인트 키는 침해된 인스턴스 키가 스스로 위조된 상태를 체크포인트로 공인하는 것을 차단한다.
- **비용:** 레코드 서명 시 서브프로세스 IPC 오버헤드와 두 개의 키쌍을 운영·배포하는 관리 비용.
- **탈출구:** 개발 및 단위 테스트에서는 로컬 키 파일을 사용하는 `OpensslSigner`를 쓰고, 대규모 프로덕션에서는 레코드 스키마 변경 없이 HSM(하드웨어 보안 모듈), 클라우드 KMS 또는 gRPC 데몬으로 서명 백엔드를 교체할 수 있다.

### D-EV-2: 레코드 스키마 및 PEP Fail-Closed 실행 순서

증적 체인은 `intent`와 `result` 두 가지 유형의 레코드를 기록한다.

- **기본 필드:** `v`(=1), `seq`(0부터 시작하는 연속 정수), `ts_ms`(밀리초 단위 정수 타임스탬프),
  `kind`(`intent` | `result`), `instance_id`(인스턴스 식별자), `epoch`(단조 증가 정수), `grant_id`(인가 토큰 식별자),
  `invocation_hash`(호출 인자의 표준 JSON SHA-256 해시), `prev_hash`(이전 항목 해시), `entry_hash`(현재 항목 해시), `sig`(서명 hex).
- **Result 전용 필드:** `intent_seq`(해당 intent의 `seq` 번호) 및 `outcome`(`ok` | `error` | `aborted`).
- **PEP 실행 순서:**
  1. `intent` 레코드를 생성하고 체인에 추가한다.
  2. 디스크에 flush 및 `os.fsync()`로 내구성을 확보한다.
  3. PDP에서 인가 토큰을 소비한다.
  4. 실행기를 호출하여 도구를 실행한다.
  5. 1단계의 `intent_seq`를 가리키는 `result` 레코드를 추가하고 fsync한다.
- **Fail-Closed 보장:** `intent` 추가가 실패할 경우(디스크 풀, 쓰기 오류 등), PEP는 인가 토큰을 소비해서는 **안 되며**, 도구를 실행해서도 **안 된다.**

- **근거:** 기록되지 않은 비인가 실행을 원천 차단하며, 실행 중 크래시가 발생하거나 공격자가 결과를 누락하더라도 영구 기록된 intent를 통해 인가 소비 사실이 입증된다.
- **비용:** 도구 호출당 2회의 디스크 I/O 및 2회의 서명 연산 필요; 장애 발생 시 미해결(unresolved) 상태가 남을 수 있음.
- **탈출구:** 상태를 변경하지 않는 읽기 전용 쿼리는 PDP 정책 차원에서 2단계 로깅 예외를 둘 수 있으나, 상태를 변경하는 모든 도구는 2단계 증적이 강제된다.

### D-EV-3: 표준 JSON 서브셋 (Canonical JSON Subset)

레코드 직렬화는 엄격한 표준 JSON 서브셋을 사용한다:

- `json.dumps(obj, sort_keys=True, separators=(",",":"), ensure_ascii=False).encode("utf-8")`로 직렬화한다.
- 허용 타입: `str`, `int`, `bool`, `None`, `list`, `dict`.
- 부동소수점(`float`), `NaN`, `Infinity`는 **엄격히 거부**된다(`ValueError` 발생).

- **근거:** 부동소수점의 IEEE 754 표현은 언어 및 아키텍처 간 미세한 공백, 지수 표기, 정밀도 차이를 유발하여 암호학적 해시 및 서명 검증을 깨뜨린다. 결정론적 서브셋을 통해 표준 라이브러리만으로 일관된 검증을 보장한다.
- **비용:** 실수형 데이터를 직접 저장할 수 없으며, 호출자는 정수 스케일링이나 문자열 표현으로 변환해야 한다.
- **탈출구:** 임의의 정밀도를 요하는 파라미터는 호출 전에 문자열로 변환하거나 `invocation_hash` 계산 시점에 포함시켜야 한다.

### D-EV-4: 도메인 분리 해싱 및 서명

모든 해싱 및 서명 연산에는 도메인 분리 프리픽스가 적용된다:

- **엔트리 해시:** `entry_hash = sha256(b"narwhal-evidence-entry-v1\0" + canonical(entry without entry_hash, sig)).hexdigest()`.
  (`prev_hash`는 표준 본문 내부에 포함된다.)
- **엔트리 서명:** `sig = sign(b"narwhal-evidence-entry-v1\0" + entry_hash.encode())`.
- **체크포인트 서명:** `sig = sign(b"narwhal-evidence-checkpoint-v1\0" + cp_hash.encode())`.
- 제네시스 엔트리의 `prev_hash` 및 `prev_cp_hash`는 64자리 0(`"0" * 64`)을 사용하며, 서명과 해시는 소문자 hex로 저장된다.

- **근거:** 프로토콜 간 서명 치환 공격을 방지하여 엔트리 서명이 체크포인트 서명으로 오인되거나 그 반대로 악용되는 것을 방지한다.
- **비용:** 해시 및 서명 전 프리픽스 결합 및 서명/해시 필드 제거 로직 필요.
- **탈출구:** 향후 알고리즘 변경 시 `-v2\0` 등 버전 프리픽스를 올려 무중단 전환 가능.

### D-EV-5: 카운터서명 체크포인트 및 외부 내보내기 저장소

체크포인트는 주기적으로 로컬 해시 체인의 상태를 고정한다:

- **체크포인트 필드:** `v`(=1), `kind`(`checkpoint`), `cp_seq`(0부터 시작), `instance_id`, `epoch`,
  `count`(포함된 총 엔트리 수), `head_hash`(`count - 1` 위치의 엔트리 해시), `ts_ms`, `prev_cp_hash`, `cp_hash`, `sig`.
- **내보내기 저장소 (Export Store):** 체크포인트는 별도의 체크포인트 파일/저장소에 JSON 라인으로 추가된다.
  프로덕션 환경에서 PEP 작성기는 이 내보내기 저장소에 대한 **쓰기 권한이 없다.** 외부 카운터서명 에이전트가
  작성기 API의 헤드(`count`, `head_hash`)를 조회하여 체크포인트를 생성하고 독립된 `cp_key`로 서명하여 저장한다.

- **근거:** 로컬 디스크의 해시 체인만으로는 호스트 권한을 탈취한 공격자의 꼬리 자르기나 롤백 포크 공격을 탐지할 수 없다. 외부 불변 저장소에 카운터서명된 체크포인트를 기록함으로써 꼬리 자르기를 즉각 탐지할 수 있다.
- **비용:** 외부 카운터서명 서비스와 별도의 추가 전용 저장소 인프라가 필요함.
- **탈출구:** 로컬 개발 및 테스트에서는 CLI `checkpoint` 명령으로 직접 파일에 서명할 수 있으며, 프로덕션에서는 AWS S3 Object Lock 등 WORM 규격을 연결한다.

### D-EV-6: 엄격한 다중 체크포인트 검증 및 소견 분류

검증 함수 `verify(entries, entry_pub, checkpoints, cp_pub)`는 엄격한 무결성을 검증한다:

- **공개 키 필수:** `entry_pub`과 `cp_pub`은 필수 인자이며 `None` 전달 시 `TypeError` 또는 `ValueError`를 발생시킨다. 두 공개 키가 같으면 검증이 실패한다.
- **구조적 무결성:** `seq`는 0부터 연속되어야 하고, `prev_hash` 체인이 일치해야 하며, 모든 해시와 Ed25519 서명이 유효해야 한다. 단일 `instance_id` 및 단조 증가 `epoch`를 검증한다.
- **체크포인트 검증:** `cp_seq` 연속성, `prev_cp_hash` 연결, 서명 유효성, `count` 및 `epoch`의 단조 증가를 확인한다. 최신 체크포인트 기준으로 `len(entries) >= count` 및 `entries[count - 1].entry_hash == head_hash`를 강제한다(불일치 시 꼬리 자르기 또는 포크로 간주하여 실패).
- **관계 무결성:** 모든 `result`는 동일한 `grant_id`와 `invocation_hash`를 가진 이전 `intent_seq`를 참조해야 한다. 동일 `grant_id`에 대한 중복 `intent`는 실패(이중 소비 차단)하며, 동일 `intent`에 대한 중복 `result`도 허용되지 않는다.
- **소견 분류 및 종료 코드:**
  - **종료 코드 1 (무결성 실패):** 데이터 변조, 서명 불일치, 순서 누락, 체크포인트 불일치, 롤백, 이중 소비 등 침해 징후.
  - **종료 코드 0 (정상 / 경고):** 무결성 검증 통과. 결과가 없는 진행 중인 intent("consumed, outcome unknown") 및 최신 체크포인트 이후의 미고정 엔트리(`unanchored_tail = len(entries) - count`)는 소견(findings)으로 보고된다.
  - **종료 코드 2 (미해결 intent 존재):** `--fail-on-unresolved` 옵션 지정 시 결과가 누락된 intent가 하나라도 있으면 종료 코드 2를 반환한다.

- **근거:** 능동적인 악의적 위변조(코드 1)와 정상적인 실행 중 크래시(코드 0/2)를 명확히 구분하여 CI/CD 및 보안 모니터링 자동화에 명확성을 제공한다.
- **비용:** 전체 체인을 순회하며 관계형 인덱싱을 수행하는 검증 오버헤드.
- **탈출구:** 대량의 로그를 처리하는 환경에서는 기검증된 체크포인트까지의 상태를 캐싱하여 증분 검증을 수행할 수 있다.

### D-EV-7: fsync 내구성 및 오픈 시점 무결성 검증

- **내구성:** 항목 추가 시 JSON 라인 쓰기, `file.flush()`, `os.fsync(file.fileno())`를 즉시 수행한다. 파일 생성 시 부모 디렉터리도 fsync한다.
- **오픈 시점 검증:** 작성기가 기존 체인 파일을 열 때 `entry_pub`을 사용해 체인 전체를 검증한다. 끝부분이 손상되었거나 유효하지 않으면 오픈을 거부하고 예외를 발생시킨다. **묵시적 자동 복구나 잘라내기는 엄격히 금지된다.**
- **리더 동작:** 파싱 불가능한 깨진 라인이 존재하면 무결성 실패로 처리한다.

- **근거:** 전원 차단 시 버퍼 누락으로 인한 로그 손실을 방지하고, 공격자가 "크래시 복구"를 핑계로 체인 끝을 임의로 잘라내는 행위를 방지한다.
- **비용:** 항목 쓰기마다 동기식 디스크 I/O 지연 발생.
- **탈출구:** 읽기 전용 쿼리는 체인에 쓰지 않으므로 상태를 변경하는 인가된 작업에만 fsync 지연이 적용된다.

### D-EV-8: 재시작에 걸친 1회성 사용 도출

- 작성기는 시작 시 기존 체인을 읽어 이미 소비된 `grant_id` 목록을 메모리에 도출한다.
- 이미 체인에 존재하는 `grant_id`로 새로운 `intent`를 추가하려 하면 작성기가 즉시 거부한다.

- **근거:** 외부 데이터베이스에 의존하지 않고도 프로세스 재시작이나 노드 재부팅을 넘나드는 1회성 사용 보장을 달성한다.
- **비용:** 활성 인스턴스 메모리에 소비된 grant 목록을 유지해야 함.
- **탈출구:** 장기 실행 인스턴스의 경우 향후 에포크 기반 만료 정책을 통해 메모리 가비지 컬렉션을 도입할 수 있다.

### D-EV-9: 호출 해시 기반 프라이버시

- 증적 레코드에는 원시 인자를 저장하지 않고, 표준 직렬화된 호출 요청의 SHA-256 해시값인 `invocation_hash`만 저장한다.
- 원시 파라미터는 로컬 휘발성 실행 로그나 호출자 측 감사 저장소에만 격리 보관된다.

- **근거:** 자격 증명, 개인정보(PII), 비밀 토큰이 외부 검증자에게 배포되는 불변 감사 체인에 영구 노출되는 것을 방지한다.
- **비용:** 증적 체인만으로는 인자 내용을 즉시 확인할 수 없으며, 낮은 엔트로피 인자는 사전 대입 공격에 노출될 수 있다.
- **탈출구:** 향후 개선안으로 솔트가 적용된 키드 HMAC(keyed HMAC) 도입 검토 가능.

### D-EV-10: 서명 및 검증을 위한 격리된 임시 파일 I/O

- 서명 및 검증 연산 시 표준 입력(`stdin`) 또는 `-in /dev/stdin`을 통해 메시지를 전달하는 것을 **엄격히 금지**한다.
- Linux 환경에서는 파이프의 `st_size=0`으로 인해 OpenSSL이 "Could not allocate 0 bytes" 오류를 발생시키며, macOS 환경에서는 쓰기 전 stat 경쟁 상태(race condition)로 인해 빈 데이터나 잘린 데이터에 서명되는 취약점이 발생한다.
- 참조 구현은 0700 권한의 임시 디렉터리 내에 0600 권한의 임시 파일(`tempfile.mkstemp` inside `tempfile.mkdtemp`)을 생성하여 메시지 및 서명을 기록하고 `-in <file>` 및 `-sigfile <file>`로 전달한다. 모든 임시 파일과 디렉터리는 `finally` 블록에서 무조건 삭제된다.

- **근거:** Linux와 macOS 전반에서 파이프 할당 실패나 경쟁 상태 없이 임의의 동시성 환경에서도 서명 메시지 무결성을 완벽히 보장한다.
- **비용:** 서명 작업마다 일시적인 파일시스템 I/O 발생.
- **탈출구:** 향후 고성능 환경에서는 공유 메모리 또는 gRPC/UNIX 소켓 기반 아웃오브프로세스 서명기로 대체 가능.

### D-EV-11: 엄격한 체인 및 체크포인트 파일 읽기

- 검증기, CLI 및 체인 리더는 누락되었거나 읽을 수 없는 체인 파일 또는 명시적으로 전달된 체크포인트 파일에 대해 하드 에러(종료 코드 1)를 반환하며, 절대로 빈 성공(empty-list PASS)을 허용하지 않는다.
- 체크포인트가 없는 미고정 체인 검증은 호출자가 `--no-checkpoints` 플래그를 명시적으로 전달한 경우에만 허용된다(`unanchored_tail=전체`로 보고).

- **근거:** 증적 로그 경로가 잘못 설정되었거나 공격자가 파일을 은폐한 경우 침묵 통과(silent pass)되는 보안 결함을 원천 차단한다.
- **비용:** 체크포인트 없이 검증할 때 호출자가 명시적 CLI 플래그를 지정해야 함.
- **탈출구:** 없음; 파일 누락 시 fail-closed 원칙 필수 적용.

### D-EV-12: 모든 체크포인트 헤드 전수 검증

- `verify()`는 최신 체크포인트 레코드만 확인하는 것에 그치지 않고, 외부 저장소의 **모든** 체크포인트를 체인 항목(`entries[count-1].entry_hash == head_hash` 및 `count <= len(entries)`)과 대조하여 전수 검증한다.
- 체크포인트의 `count` 값은 시퀀스 전반에 걸쳐 엄격히 단조 증가(non-decreasing)해야 한다.
- 각 체크포인트의 `epoch` 및 `instance_id`는 대응하는 `entries[count-1]`의 값과 정확히 일치해야 하며, 빈 `instance_id`는 건너뛰지 않고 무결성 오류로 처리된다.

- **근거:** 최신 헤드 이전의 중간 체크포인트를 위조, 변조하거나 포크를 주입하여 충돌하는 이력을 고정하려는 시도를 방지한다.
- **비용:** 체크포인트 수에 비례하여 검증 시간이 선형 증가.
- **탈출구:** 없음.

### D-EV-13: 카운터서명기 사전 검증 및 헤드 확장 검사

- CLI `checkpoint` 명령어는 인스턴스 공개 키(`--entry-pub`)를 필수로 요구하며, 체크포인트에 서명하기 전에 기존 체인 항목들의 서명과 링크를 엄격히 전수 검증한다.
- 카운터서명기는 새로운 체크포인트 헤드가 이전 체크포인트 헤드를 엄격히 확장하는지(`prev_head`가 여전히 `entries[prev_count-1]`에 존재하는지) 확인하며, 충족되지 않으면 서명을 거부한다.

- **근거:** 격리된 카운터서명기가 유효하지 않거나 변조된 체인, 혹은 분기된 체인에 맹목적으로 서명하는 것을 차단한다.
- **비용:** 체크포인트 생성 시 체인 검증 오버헤드 수반.
- **탈출구:** 없음.

### D-EV-14: 정규 DER 기반 공개 키 분리 검사

- 키 분리 가드는 파일 경로, 원시 바이트 또는 PEM 텍스트를 단순 비교하지 않고, 공개 키의 정규 DER 인코딩(`openssl pkey -pubin -outform DER`)을 추출하여 비교한다.

- **근거:** 공격자가 서로 다른 PEM 주석, 헤더 형식, 공백을 사용하여 동일한 키로 키 분리 검사를 우회하는 것을 방지한다.
- **비용:** 키페어 초기화 시 DER 추출 연산 1회 수행.
- **탈출구:** 없음.

### D-EV-15: 배타적 flock 기반 동시성 제어 및 에포크 검사

- `ChainWriter`는 파일 잠금(`str(path) + ".lock"`)에 대해 배타적 POSIX `fcntl.flock`을 획득한 상태에서만 디스크 꼬리 재검증, 무결성 확인, 레코드 추가 및 fsync의 전체 과정을 수행한다.
- 오픈 시 작성기는 호출자의 에포크가 디스크에 기록된 마지막 에포크 이상인지 검증한다.

- **근거:** 단일 호스트 내 동시 작성기 프로세스가 동일한 시퀀스 번호를 중복 추가하거나 동일 `grant_id`를 이중 소비하는 경쟁 상태를 방지한다.
- **비용:** 쓰기 작업 시 파일 잠금 획득 지연.
- **탈출구:** POSIX 호스트 필수; 분산 환경에서는 인스턴스별로 체인 파일을 분리해야 함.

### D-EV-16: 쓰기/fsync 실패 시 작성기 오염 격리

- 레코드 쓰기 또는 fsync 작업 중 디스크에 바이트가 도달했을 가능성이 있는 시점에 예외가 발생하면, 해당 `ChainWriter` 인스턴스를 영구히 오염(poisoned) 상태로 표시하고 이후의 모든 추가 및 헤드 조회를 거부한다.
- 새로운 작성기 인스턴스를 생성하여 디스크에 실제 커밋된 항목을 안전하게 재검증하고 상태를 복구해야 한다.

- **근거:** 일시적 I/O 실패 후 메모리 상태와 디스크 상태의 불일치로 인한 체인 오염을 원천 차단한다.
- **비용:** I/O 오류 발생 시 프로세스 재시작 또는 객체 재생성 필요.
- **탈출구:** 없음; fail-closed 원칙 필수.

### D-EV-17: 엄격한 정규 JSON 라인 파싱 및 형태 검사

- 체인 및 체크포인트 리더는 중복 딕셔너리 키를 거부하는 `object_pairs_hook`을 장착한 `json.loads`를 사용한다.
- 파일의 모든 라인은 바이트 단위로 `canonical(record) + b"\n"`과 정확히 일치해야 하며, 여분의 공백, 빈 라인, 키 재정렬, 비정규 직렬화는 즉시 무결성 실패를 유발한다.
- 잘못된 레코드 형태(비딕셔너리, 필수 필드 누락, 잘못된 타입)는 포착되지 않은 런타임 예외를 던지지 않고 검증 오류로 보고된다.

- **근거:** 결정론적 표준 직렬화를 강제하고 파서 차이로 인한 공격(parser differential attacks)을 방지한다.
- **비용:** 읽기 시 라인별 바이트 비교 오버헤드.
- **탈출구:** 없음.

### D-EV-18: 적대적 변이 테스트 스위트

### D-EV-21: 파일 디스크립터 기반 Inode 단위 Advisory Flock

- `ChainWriter`는 인접 `.lock` 파일 대신 체인 파일 자체의 열린 파일 디스크립터(`os.O_RDWR | os.O_CREAT`)에 대해 배타적 POSIX `fcntl.flock`을 획득한다.
- Advisory 파일 잠금은 inode 단위로 동작하므로 심볼릭 링크, 하드 링크 또는 다양한 경로 표현을 통한 접근도 동일한 기반 파일 디스크립터/inode에서 직렬화된다.

- **근거:** 심볼릭 링크나 대체 경로로 인접 `.lock` 파일을 우회하는 동시성 레이스 취약점을 차단한다.
- **비용:** 쓰기 작업 중 파일 디스크립터 유지 관리. Flock은 advisory 잠금임.
- **탈출구:** 로컬 POSIX 파일시스템에서는 없음.

### D-EV-22: 증분 검증 캐싱 및 O(신규 엔트리) 추가 비용 모델 (D-EV-28로 일부 대체)

- `ChainWriter`는 초기화 시 체인을 전수 검증하고 `(count, head_hash, last_seq, epoch, consumed_grants, offset, last_entry_offset)`을 캐싱한다.
- 이후 잠금을 획득한 상태에서 엔트리를 추가할 때 파일 크기 변경 여부를 확인한다:
  - 파일이 잘렸거나(`st_size < cached_offset`) `cached_count - 1` 위치의 엔트리가 `cached_head_hash`와 불일치하면, 열린 작성기는 즉시 자신을 오염(poison) 처리하고 예외(`ChainIntegrityError`, D-EV-28)를 발생시킨다. **어떠한 침묵 복구(silent recovery), 재읽기 또는 자동 잘라내기도 허용되지 않으며**, 메모리 내 소진된 인가 목록은 절대로 폐기되지 않는다(키 없는 이중 사용 우회 방지). 오직 새로운 `ChainWriter` 오픈 시에만 디스크 전수 검증을 수행한다.
  - 다른 프로세스에 의해 새 바이트가 추가된 경우(`st_size > cached_offset`), 새로 추가된 라인만 읽어 `entry_pub`으로 검증하고 캐시에 반영한다.
  - 동시 쓰기가 없는 정상 상태에서는 검증 subprocess 호출 0회, 서명 subprocess 호출 1회(체인 길이에 무관한 O(1))로 추가된다.

- **근거:** 순차 체인 쓰기 시 O(N^2) 2차 확장을 제거하여 처리량을 대폭 향상하면서도 오픈 시점의 무결성 검증을 온전히 유지하고, 단축된 파일에 대한 침묵 재읽기로 인한 키 없는 이중 인가 소진 우회를 원천 차단한다.
- **비용:** 메모리 내 캐싱 및 파일 오프셋 추적 오버헤드.
- **탈출구:** 없음; 열린 작성기는 파일 단축 또는 변조 시 즉시 오염되며, 디스크 기반 전체 재검증은 신규 `ChainWriter` 초기화 시에만 허용된다.

### D-EV-28: 파일 단축 또는 헤드 불일치 시 작성기 즉시 오염

- **근거:** 열린 작성기에서 단축된 파일을 조용히 다시 읽으면 이미 소비된 인가 기록이 메모리에서 유실되어 이중 소비 창이 열리는 취약점을 차단한다.

- **탈출구:** 새로운 `ChainWriter` 오픈은 디스크에 잔존하는 유효 레코드를 스캔하여 검증한다.

### D-EV-29: 쓰기 전 입력 유효성 및 경계 검사

### D-EV-31: 파일 교체 (Rename Swap) 탐지

- `ChainWriter` 및 CLI `checkpoint` 카운터서명기는 획득한 flock 하에서 `os.fstat(locked_fd)`와 `os.stat(path)`가 `st_ino` 및 `st_dev`에서 일치하는지 확인한다.
- 작성기가 파일 디스크립터를 열고 있는 동안 공격자가 원자적 rename/replace로 파일을 교체하면, 작성기는 다음 작업 시 불일치를 감지하고 즉시 자신을 오염시킨다.

### D-EV-36: 카운터서명기 원자성 및 잠금 순서 보장

- `cmd_checkpoint`는 체크포인트 내보내기 파일(`os.O_RDWR | os.O_CREAT`)에 대해 기존 체크포인트 읽기 -> 검증 -> 체인 파일에 대한 `LOCK_SH` 획득 -> 체인 읽기 및 검증 -> 체크포인트 생성 -> 서명 -> 추가 -> fsync 전체 시퀀스 동안 배타적 잠금(`fcntl.LOCK_EX`)을 유지해야 한다.
- 잠금 계층 구조는 엄격히 정의된다: **체크포인트 파일 먼저(`LOCK_EX`), 그 후 체인 파일(`LOCK_SH`)**. 시스템 어디에서도 역순 잠금은 존재하지 않는다.
- 새 체크포인트는 반드시 체인을 전진시켜야 한다(`count > prev_count`). 만약 `count <= prev_count`이면 카운터서명기는 명확한 오류 메시지와 함께 0이 아닌 코드로 종료하며, 경쟁에서 진 프로세스는 절대로 중복된 `cp_seq` 번호를 작성하지 않는다.

- **근거:** 동시 카운터서명기가 중복된 `cp_seq` 번호를 생성하거나 내보내기 저장소를 손상시키는 경쟁 조건을 방지한다.
- **비용:** 체크포인트 내보내기 작업의 직렬화.
- **탈출구:** 체크포인트는 주기적으로 생성되므로 직렬화가 작성기 성능에 영향을 주지 않는다.

### D-EV-37: 카운터서명기 기존 체크포인트 사전 검증

- **근거:** 카운터서명기가 이미 침해되었거나 변조된 체크포인트 저장소에 유효한 서명을 덧붙이는 것을 방지한다.

### D-EV-41: 제네시스 체크포인트 헤드 앵커 및 검증기 키 타입 엄격성

### D-EV-43: 손상된 체크포인트 라인 복구 절차 (Recovery from a torn checkpoint line)

#### Recovery from a torn checkpoint line

- 검증기(verifier)와 카운터서명기(countersigner)는 손상된(torn, 부분 기록된) 라인이 포함된 체크포인트 저장소를 올바르게 거부한다(fail-closed).
- Append-only 저장소는 제자리에서 수정하거나 잘라낼 수 없다.
- 복구 절차: 손상된 저장소를 증적으로 읽기 전용 보관(archive)하고, 새로운 에포크(NEW epoch, 체인 작성기의 epoch도 반드시 함께 증가) 하에서 `cp_seq = 0`으로 새 저장소를 시작하며, 구 저장소의 마지막 유효 체크포인트 해시(`cp_hash`)를 장애/사건 기록에 기재한다.
- **잔여 위험:** 새 에포크 이전의 과거 이력은 보관된 구 저장소에 의해서만 앵커링된다.

- **근거:** 불변 WORM 스토리지 손상 시 fail-closed 불변식을 훼손하지 않는 표준 운영 복구 절차를 수립한다.
- **비용:** 수동 장애 대응 및 에포크 증가 운영 비용.
- **탈출구:** 없음.

## 프로토콜 시퀀스

에이전트 거버넌스 구성 요소 간의 정상 라이프사이클 및 실패 동작은 다음과 같다:

```text
호출자 / PEP               서명기 (Signer)           증적 파일 (Disk)          실행기 (Executor)
     |                          |                          |                     |
     |--- 1. intent 생성 ------>|                          |                     |
     |    (grant_id, hash)      |                          |                     |
     |<-- 엔트리 서명 ----------|                          |                     |
     |--- 2. append_intent ------------------------------->| (fsync)             |
     |                                                     |                     |
     |=== 3. grant 소비 (PDP) ===                          |                     |
     |                                                                           |
     |--- 4. 도구 실행 --------------------------------------------------------->|
     |<-- 실행 결과 반환 --------------------------------------------------------|
     |                                                                           |
     |--- 5. result 생성 ------>|                          |                     |
     |    (intent_seq, outcome) |                          |                     |
     |<-- 엔트리 서명 ----------|                          |                     |
     |--- 6. append_result ------------------------------->| (fsync)             |
```

### 단계별 실패 처리 및 검증기 보고 동작

| 실행 단계 | 실패 조건 | PEP 시스템 동작 | 체인 상태 | 검증기 보고 내용 |
|---|---|---|---|---|
| **1-2. Intent 기록** | 디스크 풀, 쓰기 오류, 권한 부족 | **Fail-closed:** 즉시 중단. 인가를 소비하지 않으며, 실행기를 호출하지 않음. | 레코드 추가되지 않음. | 정상 (기록 없음). 이중 소비 없음. |
| **3. Grant 소비** | PDP 통신 실패, 네트워크 타임아웃, 인가 만료 | 실행 중단. result를 생성하지 않음. 로컬 체인에서 인가는 소비된 상태로 남음. | intent만 기록되고 result 없음. | 소견: "consumed, outcome unknown". 종료 코드 0 (옵션 시 2). 재사용 불가. |
| **4. 도구 실행** | 프로세스 크래시, OOM, 호스트 전원 차단 | 실행 중 비정상 종료. result가 기록되지 않음. | intent만 기록되고 result 없음. | 소견: "consumed, outcome unknown". 감사에서 잠재적 부분 실행 추적. |
| **5-6. Result 기록** | 실행 완료 후 디스크 오류로 result 쓰기 실패 | 실행은 완료되었으나 성공 증적이 남지 않음. | intent만 기록되고 result 없음. | 소견: "consumed, outcome unknown". 호스트가 실행 사실을 부인할 수 없음. |
| **전체 완료** | 정상 실행 경로 | intent와 result가 모두 기록되고 fsync 완료. | 두 항목이 모두 체인에 연결됨. | 무결성 검증 통과 (PASS). 종료 코드 0. |

## 잔여 위험 (Residual Risks)

암호학적 무결성 보장에도 불구하고 다음과 같은 잔여 위험이 존재한다:

1. **서명 오라클(Signing Oracle):** 작성기 프로세스는 비공개 키를 보유하지 않으나, PEP 호스트의 root 권한이나 실행 런타임을 장악한 공격자는 로컬 서명 프로세스에 임의의 새 미고정 엔트리 서명을 요청할 수 있다. 이는 외부 WORM 저장소로 내보내지는 잦은 카운터서명 체크포인트와 서명기 경계에서의 속도/정책 제한을 통해서만 완화된다.
2. **Advisory POSIX Flock 및 공유 파일시스템 한계 (NFS 주의사항):** 체인의 동시성 제어는 체인 파일 자체의 열린 파일 디스크립터에 대한 `fcntl.flock`에 의존한다. POSIX 시스템에서 `fcntl.flock`은 권고 잠금(advisory lock)이므로, 잠금을 획득하지 않는 비협조적 프로세스는 파일에 여전히 쓸 수 있다. 또한 네트워크 파일시스템(NFS)이나 분산 파일시스템에서는 flock 동작이 신뢰할 수 없거나, 논블로킹이 지원되지 않거나, 비활성화되어 있는 경우가 많다. 증적 체인은 엄격히 로컬 POSIX 파일시스템을 요구하며, 분산 다중 호스트 에이전트는 단일 네트워크 마운트 파일을 공유하는 대신 독립된 체인 파일을 유지해야 한다.
3. **대역 외(Out-of-band) 체크포인트/앵커 전달 전제 및 명시적 옵트인:** 검증기는 신뢰할 수 있는 체크포인트 저장소나 예상 고정 카운트를 대역 외로 전달받아야 한다. 비어 있는 체크포인트 파일이나 빈 목록을 제공하는 것은 하드 에러로 처리된다(D-EV-20). 공격자가 검증 입력을 가로채더라도 빈 체크포인트 파일로 검증을 우회할 수 없으며, 체크포인트 없는 체인을 검증하려면 호출자가 `--no-checkpoints`(또는 API `allow_no_checkpoints=True`)를 명시적으로 지정해야 하고, 이 경우 `unanchored_tail=전체`가 명시적으로 보고된다.
4. **재사용 방지 보장의 범위 한계 및 재시작 시 1회성 사용:** 열린 `ChainWriter`는 소진된 모든 인가를 메모리에 유지하며 파일 단축이나 변조를 탐지하는 즉시 자신을 오염시켜 활성 작성기에서의 키 없는 이중 인가 소진(spend-spend) 재사용을 방지한다(D-EV-28). 그러나 작성기는 체크포인트를 읽지 않으므로, 프로세스 재시작 후 체인 파일이 단축되어 있었다면 재시작된 작성기는 잔존하는 온디스크 엔트리만을 기준으로 소비된 인가를 도출하게 되어 이미 이전 체크포인트에 고정(anchored)되었던 인가를 재소비할 수 있다. 검증기는 체크포인트 저장소와 대조할 때 이 이중 소비를 탐지(종료 코드 1)한다. 따라서 재시작에 걸친 쓰기 시점의 1회성 사용은 최선(best-effort) 보장이며, 정책 결정 지점(PDP)이 대역 외에서 인가 토큰의 유효 기간을 제한해야 한다.
5. **체크포인트 저장소의 WORM 불변성 전제:** 체크포인트 파일이 저장되는 외부 저장소가 추가 전용(WORM, 예: AWS S3 Object Lock 준수 모드 또는 GCP Bucket Lock)이어야만 꼬리 자르기와 포크를 방지할 수 있다. 공격자가 체크포인트 저장소까지 삭제할 수 있다면 롤백 탐지가 불가능하다.
6. **인스턴스 키 인증 및 에포크 롤오버 생명주기:** 본 참조 규격은 로컬 공개 키 검증을 다루며, PKI 인증서 발급, 키 폐기 목록, SPIFFE/TPM 기반 하드웨어 증명 및 자동 에포크 교체는 외부 배포 플랫폼의 몫으로 남겨둔다.
7. **낮은 엔트로피 인자 추측:** 솔트 없는 SHA-256 `invocation_hash`는 불리언 값이나 단순 열거형 인자의 경우 무차별 대입이나 레인보우 테이블 공격을 통해 원래 인자를 추측할 수 있다.
8. **표준 JSON 서브셋의 한계:** RFC 8785(JSON Canonicalization Scheme)의 전체 구현이 아닌 Python 표준 라이브러리 기반 서브셋이므로, 타 언어로 재구현할 경우 부동소수점 배제 및 정렬 규칙을 엄격히 따라야 한다.
9. **참조 구현 단계:** 본 문서는 `scripts/evidence/`의 참조 알고리즘과 CLI를 정의하며, 실제 Envoy/Istio와 같은 프로덕션 PEP 게이트웨이 파이프라인 배선은 향후 과제다.
10. **증분 캐싱 후 추가 비용 모델 (D-EV-22):** 정상 상태에서 엔트리 추가는 암호화 작업 기준 O(1)로 동작한다: 정확히 1회의 Ed25519 서명 subprocess 호출과 0회의 검증 호출, 그리고 O(새 바이트) 디스크 I/O만 소요된다. 신규 작성기 초기화(fresh open) 또는 프로세스 재시작 시에만 전체 이력 서명을 검증하는 O(체인) 전체 검사를 수행하며, 이미 열려 있는 작성기가 파일 단축을 만나면 침묵 복구 없이 즉시 오염된다(D-EV-28).
11. **Advisory Flock 및 Rename-Swap 잔여 위험 (D-EV-31):** POSIX `fcntl.flock`은 권고 잠금이므로 디렉터리 쓰기 권한을 가진 공격자나 비협조적 프로세스가 체인 파일을 원자적으로 교체(`os.rename`/`os.replace`)할 수 있다. `ChainWriter`는 잠금을 획득한 상태에서 `os.fstat(locked_fd)`와 `os.stat(path)`의 `st_ino`/`st_dev` 일치 여부를 검사하여 추가 시점에 rename-swap을 최선(best-effort)으로 탐지하며, 불일치 시 다음 추가 시도에서 즉시 오염된다.
12. **Short-Write 처리 (D-EV-32):** 시그널 중단이나 논블로킹 fd 동작으로 인한 부분 쓰기(short write)를 방지하기 위해 모든 레코드 추가는 `os.fsync`를 호출하기 전에 모든 바이트가 디스크 fd에 기록될 때까지 `os.write` 루프를 순회한다. 쓰기 또는 fsync 도중 예외가 발생하면 작성기는 즉시 오염되어 fail-closed된다.
13. **잠금 계층 구조 및 카운터서명기 원자성 (D-EV-36):** 교착 상태를 방지하기 위해 잠금 계층 구조가 엄격히 정의된다: 카운터서명기는 체인 파일에 대해 `fcntl.LOCK_SH`를 획득하기 전 체크포인트 내보내기 파일에 대해 전체 카운터서명 주기 동안 `fcntl.LOCK_EX`를 유지한다. 시스템 내 어떠한 구성 요소도 역순(체인 파일 후 체크포인트 파일)으로 잠금을 획득하지 않는다. 경쟁에서 밀린 동시 카운터서명기는 체인이 전진하지 않았음(`count <= prev_count`)을 탐지하고, 서명을 거부하며 중복 체크포인트를 작성하지 않고 0이 아닌 종료 코드로 종료한다.

| **CLI 체크포인트 확장 검사 (D-EV-26)** | 이전 헤드를 확장하지 않는 새 헤드로 체크포인트 시도 | 카운터서명기가 비확장 헤드 서명 거부 | 종료 코드 1 |
| **체크포인트 XOR 상호 배제 (D-EV-26)** | checkpoints와 no-checkpoints 둘 다 지정 또는 둘 다 누락 | 엄격한 XOR 검증 오류 | 종료 코드 1 |
| **중복 JSON 키 독립 검증 (D-EV-26)** | 중복 키가 포함된 라인을 직접 파싱 | object_pairs_hook이 중복 키 거부 | 예외 발생 |
| **생성 시 디렉터리 fsync (D-EV-26)** | 새 디렉터리에 첫 쓰기 시 디렉터리 fsync 수행 | 디렉터리 fd fsync 호출 확인 | 내구성 보장 |
| **심볼릭 링크 작성기 직렬화 (D-EV-26)** | 심볼릭/하드링크를 통한 복수 작성기의 동일 grant 경합 | inode 단위 flock으로 추가 직렬화 | 안전한 직렬화 |
| **증분 추가 확장성 (D-EV-22)** | 300회 추가 실행 후 300번째 추가의 subprocess 호출 수 | openssl 호출 3회 이하 확인 (O(1) 추가) | 통과 |
| **기형 레코드 형태 검증 (D-EV-23)** | 기형 타입(문자열 count, 리스트 grant, 리스트 entry 등) | 크래시 없이 구조화된 무결성 오류 반환 | 종료 코드 1 |
| **Fail-Closed 키 분리 (D-EV-25)** | 파싱 불가한 키를 keys_are_identical에 전달 | 예외 발생 / 검증 오류로 fail-closed | Fail-closed |
| **카운터서명기 원자성 (D-EV-36)** | 미진행 체인에 대한 6개 동시 카운터서명기 실행 | 정확히 1개 성공, 5개 실패; 중복 cp_seq 없음 | 안전한 직렬화 |
| **체크포인트 저장소 사전 검증 (D-EV-37)** | 체크포인트 파일 내 위조/손상된 cp0 존재 | 카운터서명기가 확장 서명 거부 | 종료 코드 1 |
| **CLI 종료 코드 (D-EV-38)** | CLI 하위 명령 인자 오류/누락 | 종료 코드 64 (EX_USAGE); 종료 코드 2는 verify 전용 | 종료 코드 64 |
| **표준 소문자 16진수 강제 (D-EV-39)** | 해시 또는 서명에 대문자/혼합 문자 포함 | 형태 검증에서 소문자 hex 불일치 거부 | 종료 코드 1 |
| **캐시된 헤드 해시 제자리 변조 탐지 (D-EV-40)** | 파일 크기를 유지한 마지막 엔트리 바이트 변조 | 작성기가 헤드 해시 불일치 감지, 즉시 오염 | Fail-closed |
| **체크포인트 count=0 앵커 (D-EV-41)** | count=0이나 제네시스 해시가 아닌 체크포인트 | 검증기가 비제네시스 앵커 거부 | 종료 코드 1 |
| **검증기 개인 키 거부 (D-EV-41)** | OpensslVerifier에 비공개 키 PEM 파일 전달 | 초기화 시 거부 (공개 키가 아님) | ValueError |

## 결과

- 에이전트 런타임이나 호스트가 침해되더라도 이미 체크포인트에 고정된 과거 이력을 변조하거나 조작할 수 없다.
- 프로세스 크래시나 재부팅 후에도 증적 체인을 통해 1회성 인가 토큰의 재사용이 차단된다.
- 2단계 intent-result 기록을 통해 상태 변경 도구의 fail-closed 실행 의미론을 확립한다.
- 표준 OpenSSL 도구와 Python 3.10 표준 라이브러리만으로 외부 의존성 없이 오프라인 검증이 가능하다.

## 검토한 대안

- **단일 대칭키 HMAC 로깅:** HMAC 검증에 비밀 키가 필요하여 제3자 감사관이나 멀티테넌트 환경에서 검증 권한을 안전하게 위임할 수 없어 기각했다.
- **블록체인 또는 분산 원장 직접 기록:** 과도한 지연 시간, 높은 리소스 비용, 외부 네트워크 의존성으로 인해 Narwhal의 에어갭 격리 원칙에 위배되어 기각했다.
- **외부 syslog / Fluentd 전송에만 의존:** 네트워크 전송 데몬만으로는 로컬 2단계 intent-result 원자성과 암호학적 비부인성을 보장할 수 없어 기각했다.
- **외부 프로토타입 `shagunlabs/mcp-guard` 채택:** 검토 시점에 핵심 감사 기능이 미구현 상태("Not yet built")였으며, 암호학적 체크포인트와 2단계 커밋 순서 보장이 없어 채택하지 않았다.
