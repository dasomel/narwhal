| 2026-08-02 | Checked whether phase 2 was still running with `pgrep -f 06-phase2-start` over ssh. The pattern matched the ssh command line carrying it, so a job that had finished 28 hours earlier reported RUNNING every time it was polled. Same shape as the `pkill -f '6443:127.0.0.1:6443'` that killed its own invocation earlier in this work | `pgrep`/`pkill` patterns are matched against every process including the one asking. Confirm from the artefact instead — the log's last line and its mtime said "finished" plainly. This has now bitten three times in one exercise (`pkill -f '6443:…'` killing its own invocation, phase 2 reported RUNNING for 28 hours, and `pgrep -cf` counting the ssh that carried it), so treat any process-name check over ssh as wrong by default |

Compounding it, `git log` authorship cannot separate the sessions at all: `user.name` is `Antigravity` for every commit in this repo, and a claim was made in review that a commit came from "another agent" on exactly that non-signal | Stage the paths your task touched, never `git add -A`, and re-check `git status` immediately before committing — in a repo with concurrent sessions the tree is not yours alone. | 2026-07-31 | **Three of the four pod filters in `cluster-heal.sh` had the wrong field indices**, and the class failed in both directions. Failing OPEN: the Cilium filter read a `-n kube-system` query with the `-A` layout — `awk '$3!="1/1" && $3!="2/2" \|\| $4!="Running"'` — so it compared STATUS to `"1/1"` and RESTARTS to `"Running"`, both always true, and the next line force-deleted all 6 healthy cilium pods plus the operator. The 2026-07-30 rule below would have caught the open case: run the checker against a known-good subject and confirm it selects **nothing**.
