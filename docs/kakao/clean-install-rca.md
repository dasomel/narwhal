# RCA — Kakao Cloud 클린 설치 (2026-07-29 ~ 08-01)

> 개별 사건 기록은 [`../common/lessons-log.md`](../common/lessons-log.md)에 날짜별로 있다.
> 이 문서는 그 38건을 관통하는 **원인의 구조**를 정리한다.

## 1. 요약

Kakao Cloud에 클린 설치를 다시 수행하고 기존 오류의 재발 여부를 확인하려 했다. 재발한
기존 오류는 **없었다** — 대신 **한 번도 실행된 적 없던 경로**에서 19건의 결함이 새로 드러났다.

가장 큰 사건은 NFSv4.1 양방향 교착으로, 클러스터 스토리지를 **약 24시간** 정지시켰다.

| 항목 | 값 |
|------|-----|
| 기간 | 2026-07-29 ~ 08-01 |
| 발견·수정 결함 | 19건 (그중 3건은 수정 과정에서 새로 만든 것) |
| lessons-log 추가 | 38행 |
| 커밋 | 26건 |
| 최장 영향 | NFS 교착 ~24시간 |
| 인프라 재생성 | 노드 6대 1회, 인스턴스 교체 1회 |

## 2. 핵심 원인

> **클린 설치 경로는 한 번도 끝까지 실행된 적이 없었다.**

이 클러스터는 항상 **사람이 단계별로** 올렸다. 막히면 그 자리에서 손으로 메우고 다음으로
갔다. 그 메움은 커밋되지 않았고, 문서에도 남지 않았다. 결과적으로 리포에 기록된 절차
(`stage-kakao-nodes.sh` → `provision-kakao.sh all`)는 **처음부터 동작할 수 없는 절차**였다.

나머지 18건은 대부분 이 하나의 따름정리다. 자동화가 없으면 결함은 "사람이 그때그때 처리한
일"과 구분되지 않으므로, 결함으로 인식조차 되지 않는다.

## 3. NFSv4.1 교착 — 상세

### 증상

gitea가 5시간 넘게 `Init:0/3`, ArgoCD application 0개, 비정상 파드 10개 중 8개가 worker-1에
집중. NFS 마운트가 110초 후 타임아웃.

### 메커니즘

```
서버 (master-1)                          클라이언트 (worker-1)
nfsd4_destroy_session                    nfs4_destroy_clientid
  → nfsd4_probe_callback_sync              → rpc_call_sync
    → __flush_workqueue                       → rpc_wait_bit_killable
      → wait_for_completion                      "서버 응답 대기"
         "콜백 워크큐 배출 대기"
```

서버는 세션을 닫으려면 콜백 워크큐를 비워야 하고, 그 큐에 든 작업이 **바로 그 클라이언트로
가는 RPC**다. 클라이언트는 clientid를 해제하려면 서버 응답이 필요한데, 그 응답을 보낼 nfsd
스레드가 위에서 묶여 있다.

**워크큐는 전 클라이언트가 공유한다.** 그래서 노드 하나가 응답을 멈추면 클러스터 전체
NFS가 선다.

### 왜 재부팅이 듣지 않았나

한쪽만 재부팅하면 살아남은 쪽이 같은 세션 쌍을 몇 분 안에 다시 만든다. 양끝을 **동시에**
초기화해야 끊긴다. 이 성질 때문에 "복구했다 → 몇 분 뒤 재발"이 세 번 반복됐다.

### 왜 Vagrant에서는 없었나

같은 코드, 같은 커널, 같은 마운트 옵션이다. 차이는 **부하와 타이밍**이다. 클라우드 쪽은
파드 재스케줄과 세션 회전이 잦아 `destroy_session`과 `destroy_clientid`가 겹칠 확률이 훨씬
높다. 즉 Vagrant에도 같은 지뢰가 있었고 밟히지 않았을 뿐이다.

### 조치

NFSv3로 전환했다. v3는 상태가 없어 clientid도, 세션도, 콜백 워크큐도 존재하지 않으므로
이 순환이 **성립 불가능**하다.

대가로 NLM(락)이 서버→클라이언트 별도 연결을 쓰므로 mountd/statd/lockd 포트를 고정하고
보안그룹에 열었다.

### 검증

```
Postgres    2/2, Cluster in healthy state
PVC         14개 Bound
PV          전부 nfsvers=3
nfs4 마운트   0개 (전 노드)
D-state     0 (전 노드)
hung task   0 (전 노드)
```

## 4. 원인 분류

19건을 원인의 성격으로 묶으면 일곱 갈래다. 개별 수정보다 이 분류가 재발 방지에 쓸모 있다.

### A. Vagrant 박스가 공짜로 주던 것 (6건)

박스에 미리 들어 있어 **필요하다는 사실이 기록될 기회가 없었던** 것들.

`nfs-common` · `ip_forward`/`br_netfilter` · `yq` · `jq` · 노드 간 무제한 통신 ·
서비스 도메인을 답하는 노드 리졸버.

`yq`가 대표적이다. `kubeadm init` **성공 직후** `yq: command not found`로 죽어서, 로그만
보면 컨트롤플레인 실패로 읽힌다. 실제로는 패키지 하나가 없었다.

> 검사 R22가 이 계열을 일반화한다 — 스크립트가 쓰는데 어떤 스크립트도 설치하지 않는
> 도구를 잡는다.

### B. 사람 머릿속에만 있던 단계 (3건)

`proxy` 단계 · `registry` 단계 · `skopeo` 설치.

앞의 둘은 스크립트가 **이미 있었는데 아무도 호출하지 않았다.** 문서의 빠른 시작에도 없었다.
드라이버의 존재 이유가 "클라우드에는 Vagrantfile 같은 순서 정의가 없다"는 것이므로,
머릿속에만 있는 단계는 곧 드라이버가 빠뜨린 단계다.

### C. 실패를 성공으로 보고 (4건)

- `all`이 `stage_a && stage_b && …` 한 줄이라 실패해도 rc=0
- 정보용 `kubectl get ...`이 스크립트 종료 코드를 결정 (5개 스크립트)
- SSH 전송 오류를 작업 실패로 오인
- **무조건 찍히는 성공 마커** (앞 항목을 고치다 내가 만든 것)

마지막 것이 가장 해로웠다. CNI 설치 실패를 `init` 성공으로 보고해 **CNI 없는 클러스터로
phase2까지** 진행시켰다. 시끄러운 실패를 조용한 실패로 바꾼 셈이라, 막으려던 문제보다
나빴다.

> 이 분류가 가장 중요하다. 여기를 먼저 고치지 않았다면 나머지 대부분이 조용히 지나가
> 훨씬 비싼 지점에서 터졌다.

### D. 도메인 분리를 넘어온 Vagrant 상수 (2건)

`NO_PROXY`의 `.local.narwhal.internal` · `NODE_IP` 폴백의 `192.168.56` grep.

둘 다 **주석은 클라우드를 이야기하는데 코드는 Vagrant를 가리키는** 형태였다.
`02-join-control-plane.sh`에는 *"Cloud: NODE_IP is supplied explicitly"*라고 적혀 있었지만
공급하는 코드가 없었다.

### E. 클라우드 의미론이 실험실과 다름 (4건)

| 차이 | 결과 |
|------|------|
| **SG가 미등록 포트를 드롭(거부 아님)** | 빠른 실패가 무한 대기로 — **3회** 발생 |
| LB에 헬스 모니터 없음 | apiserver 없는 노드로 라운드로빈, VIP 2/9 성공 |
| DNS가 IPv6 먼저 응답, v6 경로 없음 | squid `503 CONNECT tunnel failed` |
| VPC 삭제가 `PENDING_DELETE`로 고착 | 1시간 54분 후에도 미완, 재사용도 불가 |

드롭 문제가 세 번 반복된 것이 눈에 띈다. 실험실 네트워크는 거부하고, 클라우드는 침묵한다.
**"연결이 안 된다"와 "응답이 없다"는 진단이 전혀 다르다.**

### F. 아무도 읽지 않는 곳에 쓴 설정 (2건)

- `/etc/default/nfs-kernel-server` — sysv 시절 경로. systemd 유닛은 `/etc/nfs.conf`를 읽는다
- PV의 `mountOptions` — 생성 시점에 복사되므로 StorageClass를 고쳐도 기존 볼륨은 그대로

**읽히지 않는 설정 파일은 동작하는 설정 파일과 겉보기에 동일하다.** 그래서
`01-nfs-server.sh`가 이제 `rpcinfo`로 결과를 직접 확인하고 아니면 크게 실패한다.

### G. 내 판단 오류 (3건)

정직하게 남긴다. 같은 성격의 실수가 반복될 수 있기 때문이다.

| 오류 | 교훈 |
|------|------|
| 실행해 보지 않은 해결책을 문서에 씀 (2회) | README의 우회는 검증된 것으로 읽힌다 |
| 설정 변경 **후** 교착을 끊음 | 재부팅은 부팅과 첫 재마운트 사이의 창만 벌어준다 |
| StorageClass 값으로 v3 전환을 완료 판정 | 프로토콜 변경의 합격 기준은 실제 마운트와 실제 쓰기 |

보안그룹을 v4.1 교착의 원인으로 **단정한 것도 틀렸다.** 콜백 주소가 `<node>:0`이었고
v4.1 백채널은 기존 연결을 재사용한다. SG 드롭은 실재하는 문제였지만 **v3의 NLM에서
비로소 발동할** 별개 사안이었다.

## 5. 탐지 공백

이 결함들이 왜 이번에야 드러났는가.

1. **클린 설치가 CI에 없다.** 사람이 손으로 올리는 한 자동화 공백은 결함으로 보이지 않는다.
2. **실패가 실패로 보고되지 않았다.** C 분류 전체가 여기 해당한다.
3. **재실행 경로가 시험되지 않았다.** `cp -i`는 두 번째 실행에서만 발동한다. 두 스크립트
   모두 재실행을 전제한 멱등성 가드를 갖고 있으면서, 그 가드가 통과시킨 다음 줄에서
   대화형 프롬프트를 띄웠다.
4. **설정이 적용됐는지 확인하지 않았다.** F 분류.

## 6. 조치

### 완료

- 회귀 검사 도구 `scripts/test/regression-check-kakao.sh` — static 26 + runtime 13.
  각 검사가 lessons-log 항목에 대응하므로 실패가 "이미 값을 치른 어느 버그가 돌아왔다"로 읽힌다.
  `--static`은 **파괴 전에** 돌린다: 여기서 실패하면 재설치해도 같은 버그가 나온다.
- 드라이버에 `proxy`·`registry` 단계 추가, 실패 게이트(`run_stage`) 도입
- 도구 설치 명시화(yq·jq·skopeo)와 일반화 검사(R22)
- 노드 리졸버를 bastion dnsmasq로 (열거가 아닌 와일드카드 존)
- LB 헬스 모니터 4개, NFSv3 + RPC 포트 고정 + SG 규칙
- 설정 적용 여부를 **결과로** 확인(`rpcinfo` assert)

### 남은 것

| 항목 | 상태 |
|------|------|
| 고착된 VPC `4a3493e1-...` | Kakao 지원 티켓 필요. 초안: `.omc/artifacts/kakao-support-ticket.md` |
| 회귀 검사 CI (static) | **완료** — `Lint & Validate` 워크플로의 `regression-static` 잡, 매 push/PR |
| 전체 클린 설치 CI | 원격 state 백엔드가 선행 조건 (아래) |
| Vagrant 경로의 NFSv4.1 | 같은 지뢰가 남아 있다. 밟히지 않았을 뿐 |

#### 전체 클린 설치를 CI에서 돌리려면

static 회귀 검사는 이미 CI에 있다. 남은 것은 **실제로 클러스터를 세우는** 절반이고,
이것은 코드가 아니라 인프라 결정 세 가지에 막혀 있다.

1. **원격 state 백엔드** — `csp/kakao-cloud/terraform`에 `backend` 블록이 없어 state가
   로컬 파일(374 KB)이다. GitHub 러너에는 그 파일이 없으므로 `tofu apply`가 인프라를
   인식하지 못한다. **이것이 유일한 진짜 차단 요소다** — 나머지 둘은 정책 문제다.
2. **자격 증명** — `application_credential_id`/`secret`을 리포지토리 시크릿으로. SSH 키는
   terraform이 생성하므로(`local_sensitive_file`) 별도 관리가 필요 없다.
3. **비용과 시간** — 1회 약 2시간과 실제 클라우드 과금. 매 push가 아니라
   `workflow_dispatch` + 주기 실행이 현실적이다.

3회차가 무개입 완주를 보였으므로 절차 자체는 CI에 넣을 수 있는 상태다. 백엔드만 정해지면
`stage-kakao-nodes.sh` → `provision-kakao.sh all` → `regression-check-kakao.sh --all`을
그대로 잡 세 단계로 옮기면 된다.

## 8. 반복 실행 (2·3회차)

1회차가 통과했다고 절차가 반복 가능해진 것은 아니다. 노드만 교체해 같은 절차를 두 번 더 돌렸다.

| 회차 | 개입한 수정 | 결과 |
|------|-------------|------|
| 1회차 | **19건** | 완주 (매 단계 수리하며) |
| 2회차 | **5건** | 완주 |
| **3회차** | **0건** | **무개입 완주** |

2회차의 5건은 전부 **1회차에서는 구조적으로 드러날 수 없던 것**이다. 각각 전제 조건이 달랐다.

| 결함 | 드러나려면 필요했던 조건 |
|------|--------------------------|
| 드라이버에 상호배제 없음 (`flock`) | 반복 중단 — 로컬 드라이버를 죽여도 원격 셸은 완주하므로, 재개가 진행 중인 작업과 겹쳐 apt 락을 다툰다 |
| squid를 dnsmasq보다 먼저 기동 | 두 번째 클린 기동 — 수정은 들어 있는데 순서가 틀려 있었다 |
| 프로바이더 부분 실패 → 고아 인스턴스 | 인스턴스 재생성 (3회차에서는 발동하지 않음 → 간헐적) |
| 호스트 키 변경 시 조용한 exit 255 | 노드 교체 |
| gitea `RollingUpdate` + RWO 볼륨 | 타이밍 |

마지막 것이 가장 교훈적이다. 증상은 **"ArgoCD 앱 14개가 Unknown"**인데 원인은 gitea에 있었다.
차트가 `RollingUpdate` + `maxSurge=100%`로 오는데 볼륨은 RWO이고 LevelDB가 배타 락을 잡는다.
파드 둘이 뜨고 둘째가 36회 크래시하는 동안 Service는 **두 엔드포인트를 모두 유지**해,
ArgoCD의 git 요청 절반이 죽은 파드로 갔다.

> 쓰기 하나만 허용하는 볼륨에 **둘을 요구하는 전략**을 주면 안 된다. 그리고 증상이 나타난
> 곳은 원인이 있는 곳이 아니었다.

### 3회차 검증 (2026-08-03)

```
regression-check-kakao.sh --all    39/39 통과, 실패 0, 경고 0
provision-kakao.sh all             무개입 완주, phase2 FAILED 0건
노드                                6/6 Ready
ArgoCD applications                33/33 Synced + Healthy
PV                                  전부 nfsvers=3
gitea 파드                          1개 (2회차에는 2개가 충돌)
set-config-kakao.sh                노드 교체 후에도 정상 (2회차에는 조용히 exit 255)
```

**"한 번 성공한 절차"와 "반복 가능한 절차"는 다르다.** 그 차이가 2회차의 5건이었고,
3회차가 그것이 메워졌음을 보인다.

## 9. 결론

**기존 오류는 재발하지 않았다.** 세 차례 모두 회귀 검사 39개가 전부 통과했고, 과거에
고친 것들은 제자리에 있었다.

드러난 19건은 전부 **한 번도 실행된 적 없는 경로**에 있었다. 이 테스트의 가치는 개별
수정이 아니라, 문서에 적힌 절차가 실제로 동작하지 않는다는 사실을 확인한 것이다.

가장 값진 수정 하나를 꼽으면 **드라이버가 실패를 실패로 보고하게 만든 것**이다. 그것이
없었다면 나머지 대부분이 조용히 지나가 훨씬 비싼 지점에서 터졌을 것이다.
